# Implementation report — 24 October 2026

## Delivered

The existing MERN application now has a coherent botanical UI across the landing page, authentication, overview, focus timer, garden/calendar, wallet journal, challenges, friends, leaderboard and profile. Screens share a responsive shell and reusable loading/error/empty/retry states. Keyboard focus, labels, mobile navigation and reduced-motion behavior are included. Captured desktop/mobile previews are in `docs/screenshots/`; authenticated screenshots use temporary test accounts.

Authentication is persistent and consistently enforced. Profile responses omit password hashes and ownership is checked. Server time controls sessions; paused time does not count; refresh recovers the active state. Session completion, reward credit and ledger insertion share a transaction. Tree prices are fixed on the server, balances cannot be overdrawn by concurrent purchases, and operation keys prevent duplicate spending. Challenge mechanics enforce ownership, eligibility and one-time transactional credits. Social placeholders now use real requests and opt-in rankings.

API validation, consistent errors, request IDs, redacted logs, security headers, origin/request protection, rate limits and health/readiness endpoints were added. Historical arbitrary-reward and client-authored session APIs return 410. All current frontend callers use the repaired contracts.

Queries now use explicit indexes, bounded history pagination and database aggregation. Overview consolidates wallet/totals/chart data. The frontend uses route-level chunks and no longer imports overlapping chart/component/countdown libraries. The latest measured build has a 214.30 KB shared JavaScript chunk (70.96 KB gzip) and 34.24 KB CSS (8.07 KB gzip), with small lazy page chunks. No percentage speedup or server latency improvement is claimed because the baseline frontend could not build and no controlled load benchmark was run.

Development infrastructure includes non-root application containers, MongoDB replica-set persistence, startup migration/readiness gating, live source mounts, Node watch, Vite HMR, a root Makefile, a versioned migration runner with preflight/lock/status, backup commands and an independent production Compose template. Production images use multi-stage builds. CI is configured for installation, formatting, lint, tests, builds, audits, fresh migrations, browser journeys, Compose and image checks; no workflow has been pushed or run on GitHub.

## Follow-up: optional Strict focus and browser extension

Implemented Strict focus alongside normal focus. Users choose up to 30 exact website origins or page URLs before starting. The list is immutable for that session. A desktop Chromium extension checks the active tab, screen-lock state and browser focus; unapproved navigation, locking or leaving the browser interrupts the session without coins. A detected violation is saved before network access, so returning to an allowed page during an outage cannot erase it. Background tabs and quiet reading do not trigger violations. Strict sessions cannot pause; normal timer behavior is preserved.

The backend owns a 90-second monitoring deadline, checked before any strict completion. Extension alarms send check-ins approximately every 30 seconds, plus a dedicated finish alarm that bypasses ordinary heartbeat throttling. A server sweep persists expiry every 15 seconds even when the browser is closed. Late check-ins cannot revive sessions or earn rewards. Completed strict sessions use the existing transactional wallet and ledger mechanism. A hashed single-session bearer capability authorizes monitoring without exposing account credentials; visited URLs/history are not sent to the backend.

The timer includes connected/missing-extension states, allowed-link shortcuts, setup instructions, a downloadable ZIP and interruption explanations. Session recovery selects the latest created session so an expiry's effective end time cannot restore an older result. Migration `004-strict-focus` adds expiry/recovery indexes without rewriting user data. A database backup was created before applying it; users/sessions/transactions remained 1/4/3 before and after the development update. Existing migration history was preserved.

Verification completed: 13 unit/HTTP checks, 32 real-database integration checks, all 12 ordinary desktop/mobile Playwright journeys, and one real Chromium-extension journey passed (58 tests total). Extension coverage includes popup connection, allowed-page navigation, disallowed navigation, persisted violations across an injected network outage, no reward on interruption, the real finish-alarm handler, exactly-once completion, and a simulated monitoring gap. Mobile setup prevents strict start without an extension and has no horizontal page overflow. Lint, formatting, frontend build, development Docker startup/migrations, production frontend image build and ZIP integrity checks passed. The local app is healthy at `http://localhost:5179`. CI now includes the extension journey; remote CI was not run in this session.

Remaining installation/platform steps: the user must load the unpacked extension in their own browser and connect it to Bagiya; it has not been published to a store. Real Chromium extension APIs were tested. Physical laptop suspend/resume and Edge need manual platform validation. Sleep is inferred through missing check-ins; short sleep may fall within the 90-second grace period. This is a voluntary focus tool, not tamper-proof attention verification.
